## 0. 먼저 바로잡을 전제 3가지

| 요청서의 가정 | 코드·측정 결과 | 판정 |
|---|---|---|
| 원국·용신 배점이 너무 커서 일진이 묻힌다 (운세·음식) | 무작위 출생 120명 전원 `favorable_elements = []`, `confidence = low`. 용신 보완 배점은 사실상 **0점** | 틀림 |
| 사진 있는 메뉴 안에서만 추천한다 | 추천 풀은 294개(+다이어트 90개)이고 사진 여부로 거르지 않는다. 사진이 없으면 화면이 아이콘으로 대신한다 (`index.html renderMenuPhotos`) | 틀림 |
| 체질 점수가 1~3순위를 고정한다 | 고정은 맞지만 원인은 체질이 아니라 **메뉴 고유 점수**(익숙함·인기·빈도)와 카테고리 가중치 | 현상은 맞고 원인은 다름 |

더 큰 발견: 원국 방향이 비어 있어서 **같은 날이면 모든 사용자의 코디 색·행운 오행·베이직/포인트 카드가 똑같다** (3명 비교에서 14일 모두 동일). "개인화가 너무 세다"가 아니라 "개인화가 거의 없다"가 실제 상태다.
→ 용신(보완 오행)이 왜 늘 비는지는 코어(semantic) 쪽의 별도 이슈다. 의도된 보수 판정인지, 판정 기준이 너무 엄격한지 따로 확인해야 한다.

## 1. 오늘의 이야기

### 실제 원인
- 본문(daily_sections, 150문단)은 이미 일진 십성으로 날마다 바뀐다. 문제는 **톤**이다.
- 60일 × 6명 = 360일 중 관계 키가 `clash`·`friction`(조심)인 날이 **327일(91%)**, "한 가지 더"(주의 보조 메시지)가 붙은 날 **335일(93%)**, 본문에 "확인"이 들어간 날 **260일(72%)**.
- 원인: `daily.py` 가 긴장 신호에 천간극(stem_control)·해·파까지 넣고, 대운·월운과의 관계까지 센다. 천간극만 60일 동안 128번(하루 2번꼴) 걸린다. 그래서 거의 매일 "한 번 더 확인하세요"로 끝난다.
- 같은 십성은 10일마다 돌아오고, 변형 3개 중 하나를 날짜 시드로 고른다. 그래서 같은 문단이 다시 나온다 (예: 10/05·10/15 정관 본문 동일).

### 다음 단계 (아직 안 함, 문구 작업이 필요)
1. **메인 테마 4갈래를 명시**: 십성 → 테마 매핑을 데이터로 둔다.
   - 행동형: 식신·상관·편재 / 집중형: 정관·편관 / 관계형: 비견·겁재·정재 / 휴식·정리형: 정인·편인
   - 충이 걸린 날은 테마를 "정리형"으로 덮어쓴다 (일진의 변수가 메인을 바꾸는 장치).
   - 테마마다 추천 동사 풀을 따로 둔다 (행동형: 시작하다·제안하다·움직이다 / 집중형: 끝내다·좁히다 / 관계형: 묻다·건네다·함께하다 / 휴식형: 비우다·쉬다·정리하다). 현재 동사의 대부분이 "확인하다"로 몰려 있다.
2. **10일 반복 끊기**: 변형 선택을 날짜 시드 대신 일지(12지) 인덱스로 한다. 십성(10)과 일지(12)의 주기가 엇갈려서, 같은 십성이 돌아와도 다른 변형이 나온다 (같은 조합은 60일 주기).
3. **"한 가지 더" 축소**: 합(lift) 날에도 붙고 있어서 여전히 69%다. 신호가 2개 이상이거나 일지 충일 때만 붙이는 안을 제안한다.
4. 문구 확장(변형 3개 → 5개, "~날입니다" 시작 변주)은 문체 헌법에 맞춰 써야 하므로 정오님 검토 대상이다.

## 2. 음식 추천

### 실제 원인 (측정: 6명 × 60일 × 아침·점심·저녁 = 1,080회 × 2메뉴)
- 외식 모드 **된장찌개 626/2160 (29%)**, 집밥 모드 **라면 675/2160 (31%)**.
- 오행 점수가 꺼져 있다. `recommend_daily_menus` 는 `timing_element_weights is None` 일 때만 일진 오행(+6)·행운 오행(+4)을 주는데, `daily.py` 가 늘 `{}`(빈 dict)를 넘겨서 **조건이 항상 거짓**이다. 원국 방향도 비어 있으니 오행 점수는 매일 0점이다.
- 결과적으로 순위는 익숙함·인기·빈도 보너스·카테고리 가중치(`frequency * 2`)로 정해진다. 찌개(stew) 카테고리가 +10을 받고, 그 안에서는 된장찌개가 늘 1등이다.
- `main.py` 가 `recent_menus` 를 넘기지 않아 어제 추천과 겹쳐도 감점이 없다.
- 샌드위치 체감: 아침 후보 54개 중 샌드위치·토스트가 16개(30%), 집밥 모드 31개 중 빵류가 약 12개다. 사진 문제가 아니라 시간대·모드별 풀 구성 문제다.
- 각 메뉴에는 이미 오행(element)·태그(warm/cool/fresh/light/moisten…)가 붙어 있다. 오행 분포는 금64·목59·토58·수58·화55로 고르다. 매핑을 새로 만들 필요는 없고 **실제로 쓰이게** 해야 한다.

## 3. 코디

### 실제 원인
- **두 화면이 서로 다른 색 체계를 쓴다.** 홈의 베이직/포인트 카드는 `daily_copy.compose_outfit(lucky_element)`(오행 → 고정 색표)이고, "오늘의 코디 보기" 추천 1·2는 `fashion_v2` 가 Wada 2색(A·B)을 입힌 것이다. 카드에서 본 색과 코디 색이 다르다.
- 추천 1·2는 계절 × 성별 × TPO 칸마다 **고정 템플릿 2개**뿐이다 (`template_catalog.RAW_LOOKS`). 여기에 `select_template` 이 상의=화이트, 하의=베이지/차콜로 덮어쓴다. 바뀌는 건 A·B 색이 어디에 칠해지느냐뿐이다. 측정에서 남성 캐주얼은 14일 내내 "블루종 + 맨투맨/후드 + 데님/면바지"였다.
- **포인트색이 큰 옷으로 간다.** `apply_colors` 점수가 `90 + 면적*9` 이라 A색은 가장 큰 옷(블루종)으로 간다. 소품(면적 1)은 늘 진다.
- 연령 규칙이 약하다. `permitted()` 의 제한은 "50세 이상 & 추천 1 & vivid"뿐이다. 측정에서 44세 남성은 코랄·레드·페일 레드 블루종을, 51세 남성은 추천 1에서 연핑크 블루종을 받았다 (연핑크는 vivid로 분류되지 않아 50세 룰도 통과).

### 개편안
1. **색 역할 하나로 통일**: A·B 중 채도가 낮은 쪽(또는 착장 톤으로 낮춘 색)을 베이직, 높은 쪽을 포인트로 정한다. 홈 카드와 코디가 같은 두 색을 쓰게 하고, 홈 카드 색표(`daily_copy.OUTFIT`)는 은퇴시킨다.
2. **배치 규칙**: 베이직 → 아우터·상의·하의 / 포인트 → 넥타이·가방·신발·머플러·시계·모자·벨트. 도안 엔진(`assets/dalha-garments`)이 이미 그리는 소품: 넥타이·모자·시계·머플러·벨트·귀걸이·목걸이·가방·신발. **양말·스카프 도안은 없다** (만들려면 그림 작업이 필요하다).
   - 소품이 없는 템플릿(남성 캐주얼 대부분)에는 계절별 기본 소품 칸을 하나 넣는다: 가을·겨울 머플러, 봄·여름 시계.
3. **연령·성별 TPO 룰** (프로토타입 함수):
```python
LOUD_FAMILIES = {'red', 'orange', 'yellow', 'purple'}   # 분홍은 describe_color에서 red로 묶임
def loud_for_wearer(c, look):
    if c['family'] not in LOUD_FAMILIES: return False
    deep = c['lightness'] < .32 and c['saturation'] < .6    # 버건디·딥 플럼은 허용
    if look['gender'] == 'male' and look['age'] >= 35: return not deep
    if look['age'] >= 50: return not deep and c['saturation'] > .45
    return False
# permitted(): 아우터·하의·원피스에 loud 색 금지 → 포인트 칸(소품)으로만
```
   - 프로토타입으로 돌려 보니 44세·51세 남성의 레드·코랄·핑크 블루종은 사라졌다. 하지만 **이전 검토에서 고정해 둔 룩 테스트 3개와 충돌**해 테스트가 깨졌다 (fixtures/svg_accepted_looks.json 포함):
     - 55세 남성 "네이비 아우터 + 레드 터틀넥"(`test_review_requested_combinations…`) → 아우터 안에 입는 상의는 면적이 작으니 허용하는 쪽이 맞아 보인다
     - 48세 남성 카멜 아우터(`test_reported_pair…`) → 카멜이 orange로 분류됐다. 채도 기준을 넣어 중립색은 빼야 한다
   - 그래서 이 부분은 브랜치에 넣지 않고 되돌렸다. 룰 확정이 먼저다.
4. **룩 다양성**: 칸마다 템플릿을 2개 → 4~6개로 늘리고, 날짜로 서로 다른 무드 2개를 고른다 (예: 톤온톤 / 뉴트럴+포인트 소품 / 레이어드 / 셋업). 추천 1과 2는 아우터 유무·하의 종류·밝기 중 2가지 이상이 달라야 한다는 검사를 넣는다.
   - `select_template` 이 상의를 늘 화이트로 덮는 줄(`if cat=='top': item['base_color']='white'`)은 템플릿 고유색을 살리는 쪽으로 바꾼다.
   - 새 템플릿은 도안 검수(정오님 화면 확인)를 거쳐야 하므로 이 작업이 가장 길다.

## 5. 정오님이 정할 것
1. 원국 보완 오행이 모두 비는 상태를 그대로 둘지(=당분간 일진 중심), 코어 판정을 손볼지

3. 양말·스카프 도안을 새로 그릴지, 기존 소품(머플러·시계·벨트·모자·가방·신발)으로 갈지
